# nullDC DevTools

Web debugger UI for nullDC 3.0.0, the Dreamcast emulator. React 19, TypeScript, Vite.

The emulator serves the built UI and speaks the protocol described below. This repository also
contains a mock server that implements the same protocol, so the UI can be developed without an
emulator.

## Requirements

- Node.js 22 or newer.
- Rust (with the `wasm32-unknown-unknown` target) and `wasm-pack` only if you change
  `crates/aica-dsp` (see [Generated DSP module](#generated-dsp-module)).

## Generated DSP module

`src/wasm/aica-dsp/` (JavaScript glue, type declarations and the `.wasm` file used by the DSP
Playground) is generated by `wasm-pack` from `crates/aica-dsp`. It is committed, so a fresh clone
type-checks, builds and runs without a Rust toolchain.

`npm run build:dspsim` is the explicit regeneration step. `dev`, `build:native` and `build:wasm` do
not run it. After changing the crate, run it and commit the regenerated files.

## Configuration

Build time:

| Variable | Description | Default |
| --- | --- | --- |
| `VITE_TRANSPORT_MODE` | `native` (WebSocket) or `wasm` (BroadcastChannel). `build:wasm` sets it to `wasm`. | `native` |

Mock server, at run time:

| Variable | Description | Default |
| --- | --- | --- |
| `PORT` | HTTP and WebSocket port. | `5173` |
| `NODE_ENV` | `production` serves the static build from `dist-native/`. Anything else serves the sources through Vite middleware (which also opens Vite's hot-reload socket on port 24678). | unset |
| `DEBUGGER_WS_PATH` | WebSocket path of the mock server. The UI always connects to `/ws`, so keep the default. | `/ws` |

The version shown in the status bar and the About dialog is the `package.json` version, followed by
`+<git describe --tags --always --dirty>` when the build runs inside a git checkout.

## Connecting

- `native` builds open one WebSocket to `/ws` on the host that served the page (`wss:` when the
  page was loaded over https). There is nothing to configure.
- `wasm` builds use BroadcastChannel. The UI listens on `nulldc-debugger-announce` for
  `{ id, name, timestamp }` announcements and talks to the selected emulator on
  `nulldc-debugger-<id>`. It posts `ping` every second and treats three seconds without a `pong`
  as a lost connection.

With exactly one available connection the UI connects on its own; otherwise it shows a connection
picker. The status bar of a workspace shows the connection state and the endpoint.

## Protocol

JSON-RPC 2.0 in text frames over that single connection. There is no handshake and no
subscribe/unsubscribe.

- The client's first request is `debugger.describe` (params `{}`). The result contains
  `emulator` (`name`, `version`, `build`) and `deviceTree`.
- The server pushes one kind of notification, `event.tick`. Every tick is a complete snapshot:
  `tickId`, `timestamp`, `executionState`, `registers`, `breakpoints`, `eventLog`, `watches`,
  `callstacks`.
- Requests:
  - `state.getMemorySlice`, `state.getDisassembly`, `state.getCallstack`
  - `state.watch`, `state.unwatch`, `state.editWatch`, `state.modifyWatchExpression`
  - `control.pause`, `control.step`, `control.stepOver`, `control.stepOut`, `control.runUntil`
  - `breakpoints.add`, `breakpoints.remove`, `breakpoints.toggle`, `breakpoints.setCategoryStates`
  - `state.recordSgcFrames`, `state.getSgcFrameData` (answered by a JSON result followed by one
    binary frame with the recorded data)

The zod schemas in `src/lib/debuggerSchema.ts` are the reference for parameters and results, except
for the two SGC methods, which have no schema yet (see `server/mockServer.ts` and
`src/services/debuggerClient.ts`).

The mock server (`server/mockServer.ts`) keeps one shared state for all clients. It sends a tick to
every connected client after `debugger.describe`, after each request that changes state, and when a
running target hits a breakpoint. It does not push ticks periodically.

## Breakpoints

Disassembly views:

- Click the gutter to add or remove a breakpoint at that address.
- Ctrl, Cmd or Shift + click an existing breakpoint to enable or disable it.
- A filled red circle is an enabled breakpoint, an outlined one is disabled.

Breakpoint panels:

- **Events: Breakpoints**: event breakpoints by name, for example `dc.aica.channel[0].step`.
- **SH4: Breakpoints**, **ARM7: Breakpoints**: code breakpoints by hex address, for example
  `0x8C0000A0`.

Breakpoints live on the server. Every `event.tick` carries the full list, so all connected clients
show the same set.

## Mock demo deployment

`Dockerfile` builds `dist-native/` with `npm run build:native` and runs the mock server in
production mode on port 8080. `fly.toml` deploys that image.

## CI

`.github/workflows/ci.yml` runs `npm ci` and `npm run check` on Node 22 for pushes and pull
requests.
